## 2. The central design idea

The load-bearing element of your model is `user_application`, so the service was built around it:

```
Company ─→ Application ─→ Role ─→ Permission
                 ↑
Person ─→ SecurityUser ─→ UserApplication ─→ UserRole
```

- One person, **one** set of credentials.
- A **separate access grant per application**.
- Roles hang off the **grant**, not off the user.

The consequence, which the whole login flow is shaped by: **valid credentials alone authenticate
nobody.** Without an active `user_application` grant whose access window is open, login fails —
and fails with the same generic message a wrong password gets.

### Every stated decision, honoured

| Decision from the model | How it was implemented |
|---|---|
| No branches | No `branch` or `user_branch` table exists |
| `person` = data, `security_user` = credentials | Separate tables, `UNIQUE (person_id)` |
| A person can exist without a user | `person` has no required back-reference |
| A user reaches several applications | `user_application` |
| Roles and permissions belong to an application | `application_id` FK on both |
| A user's roles must match their access application | Composite FKs — see §4 |
| Sensitive tokens hashed, never plain text | SHA-256 on refresh and reset tokens |
| R2DBC at runtime, Flyway on JDBC | `spring.flyway.enabled=false` + a dedicated `FlywayConfig` bean |
| All dates `TIMESTAMPTZ` | Every date column; `OffsetDateTime` ↔ `Instant` (UTC) mapping |
| PKs `BIGINT GENERATED BY DEFAULT AS IDENTITY` | All 14 tables |
| FKs `BIGINT` (`Long` in Java) | All foreign keys |
| No UUIDs | None anywhere in the schema |

### Password hashing, to the letter

- **Argon2id**, 19 MiB memory, 2 iterations, parallelism 1
- Random 16-byte salt per password
- Full encoded string stored in `VARCHAR(255)`
- `DelegatingPasswordEncoder` for future algorithm changes
- BCrypt (cost 12) retained **for legacy verification only** — never produces a hash

A real stored value:

```
{argon2}$argon2id$v=19$m=19456,t=2,p=1$WJi/wdJ8IfvERri3ovXfJA$rs...
```

The `{argon2}` prefix is what makes a future migration undramatic: old hashes keep verifying, and
`needsUpgrade()` re-hashes them on the next successful login — the only moment the raw password is
available.

## 4. Cross-application isolation, enforced three times

This is the rule most worth getting right, so it is enforced at three independent layers:

1. **The token** — the JWT carries the authority list resolved at issuing time;
   `@PreAuthorize("hasAuthority('ROLE_ASSIGN')")` checks against it with no database read.
2. **The use case** — checks the role and the grant share an application, so the caller gets a
   clear `400` explaining the mismatch.
3. **The database** — composite foreign keys make the cross-application assignment structurally
   impossible.

The third layer is the one that matters. Verified directly against PostgreSQL:

```sql
-- grant 2 is for application 1; role 3 belongs to application 2
INSERT INTO user_role (user_application_id, role_id, application_id) VALUES (2, 3, 2);
-- ERROR: violates foreign key constraint "fk_user_role_user_application"
-- DETAIL: Key (user_application_id, application_id)=(2, 2) is not present in table "user_application".

INSERT INTO role_permission (role_id, permission_id, application_id) VALUES (3, 1, 1);
-- ERROR: violates foreign key constraint "fk_role_permission_role"
-- DETAIL: Key (role_id, application_id)=(3, 1) is not present in table "role".
```

## 6. A real bug, found and fixed

Worth recording because it was invisible from the API surface.

**Symptom.** Reuse detection appeared to work: replaying a revoked refresh token returned the
correct `401` with the correct message.

**Reality.** The revocation never persisted. `RefreshTokenUseCaseImpl` revoked the token family and
*then* threw — inside a method-wide `@Transactional`. The thrown error rolled the revocation back
with it. The replayed token stayed alive, and the protection did nothing at all.

**How it was caught.** By checking the database rather than the response:

- `refresh_token.revoked_at` was still `null` after the `401`
- the `TOKEN_REUSE_DETECTED` audit row was missing
- only a **gap in the identity sequence** (audit id 10 absent between 9 and 11) revealed that a row
  had been inserted and then rolled back

**Fix.** `RefreshTokenUseCaseImpl` now uses an explicit `TransactionalOperator` instead of
`@Transactional`. The revocation is committed in its own unit of work and the error is raised
*outside* it, while the rotation itself (revoke the old row, insert the new one) stays inside one
transaction where atomicity is what actually matters. The same treatment was applied to the
"account can no longer authenticate" path.

**Confirmed after the fix:**

```
replaying the old token:          401 Refresh token already used. Every session … revoked.
the current token died with it:   401 Refresh token already used. Every session … revoked.

 id |  family  | revoked | replaced_by_token_id
----+----------+---------+----------------------
  9 | bu3sOP6G | t       |                   10
 10 | bu3sOP6G | t       |
```

Reasoning is written up in `docs/ARCHITECTURE.md` §4.

### A second, smaller fix

`@PathVariable Long applicationId` failed at runtime with *"parameter name information not
available via reflection"*. The Spring Boot Gradle plugin adds `-parameters` only to
`:app-service`, and the controllers live in `:reactive-web`. The flag is now set for every module
in the root `build.gradle`.

## 7. Design decisions worth knowing about

### `INET` and `JSONB` handling

Neither type has a portable R2DBC Java mapping. The options were to weaken the columns to
`VARCHAR`/`TEXT`, or to put a driver-specific class into the entity model.

Instead, the four tables that use them (`refresh_token`, `login_attempt`, `password_reset_token`,
`security_audit`) are handled by `DatabaseClient` adapters with explicit SQL — `CAST(:ip AS inet)`
and `CAST(:metadata AS jsonb)` inbound, `host(ip_address)` and `metadata::text` outbound. The
columns keep their real types, and with them the validation and index behaviour that made those
types worth choosing, without any PostgreSQL type reaching the domain model.

The other ten tables map cleanly through Spring Data R2DBC repositories with MapStruct mappers.

### Concurrency

State transitions on `security_user` (failed attempt, lock, password change, stamp bump) are single
`UPDATE` statements, not read-modify-write cycles. `failed_attempts` uses
`UPDATE … SET failed_attempts = failed_attempts + 1 … RETURNING failed_attempts`, so two concurrent
login attempts cannot lose an increment.

### What the caller is told versus what is recorded

| Situation | Response | Database |
|---|---|---|
| Unknown username | `401 Invalid credentials` | `failure_reason = UNKNOWN_USERNAME` |
| Wrong password | `401 Invalid credentials` | `BAD_PASSWORD`, counter incremented |
| Account locked | `401 Invalid credentials` | `ACCOUNT_LOCKED` |
| No access to the application | `401 Invalid credentials` | `NO_APPLICATION_ACCESS` |
| Reset for an unknown user | `200` + neutral message | nothing |
| Logout with a bogus token | `200 Logged out` | nothing |

One message for every failure. The precise reason lives where an operator can see it and an
attacker cannot.

### The first administrator

`V17` seeds the company, applications, professions, roles and permissions — but not a user. A
credential row needs a real Argon2id hash, which only the running encoder can produce.
`BootstrapAdminRunner` creates the administrator on first start when
`security.bootstrap.enabled` is on, and is a no-op once the username exists, so restarting never
resets an account.

## 8. Known gaps

Stated plainly, and listed in `docs/ARCHITECTURE.md` §11.

1. **No tests are included.** Behaviour was verified by running the service against a real
   PostgreSQL and inspecting both responses and tables. That is not a substitute for a suite; the
   obvious first targets are the use cases against Testcontainers.
2. **Password reset delivers nothing.** The token is generated and stored correctly, but there is
   no mail adapter. `security.policy.expose-reset-token` returns it in the response for local
   testing and must stay off elsewhere.
3. **A revoked token always reads as reuse.** After a logout-all or a password change, presenting
   an old token returns the reuse-detection message rather than a plainer "session ended". It fails
   closed, which is the right direction, but the message is misleading.
4. **`security_stamp` is not checked per request.** By design — that would mean a database read on
   every call. It is verified at refresh, and the short access-token lifetime bounds the exposure.
5. **No rate limiting.** Lockout bounds attempts per account; it does nothing against a slow spray
   across many accounts from one address. `login_attempt(ip_address, attempted_at DESC)` is indexed
   for exactly that query, but nothing consumes it yet.

## 10. How to run it

```bash
cd /external/work/personal_projects/multiples_soluciones_para_el_agro/ms-security

# 1. PostgreSQL
podman compose -f docker/compose.yaml up -d   # or: ./docker/postgres.sh up

# 2. Environment
cp .env.example .env && $EDITOR .env && source .env
export BOOTSTRAP_ADMIN_ENABLED=true BOOTSTRAP_ADMIN_PASSWORD='Adm1n-Local-2026!'
export EXPOSE_RESET_TOKEN=true    # local only — example 5 needs to read the reset token

# 3. Build and run — Flyway creates and seeds the schema on the first start
./gradlew clean build
./gradlew :app-service:bootRun

# 4. See it all work
./docs/examples.sh
```

- Swagger UI — <http://localhost:8080/swagger-ui.html>
- Health — <http://localhost:8080/actuator/health>

Turn `BOOTSTRAP_ADMIN_ENABLED` back off once the administrator exists.
